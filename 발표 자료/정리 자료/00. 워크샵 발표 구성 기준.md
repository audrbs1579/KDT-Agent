00 KDT 교육 PM 에이전트 — 워크샵 발표 구성 기준

작성 기준: 2026-10-27 · 11/05 워크샵 · 오전 약 30분 브리핑, 발표 직후 또는 오후 논의 · 본편 **36장**

## 이 문서의 역할

설계보고서를 경영진이 이해할 수 있는 발표로 바꾸기 위한 기준 문서다. **무엇을 왜 만들려는지, 어떤 자료가 들어와 어떤 결과가 나오며, 어디서 사람이 결정하는지**를 먼저 설명한다. 현 단계는 설계와 첫 검증 범위를 공유하는 워크샵이다. 제품 출시 보고, 확정 견적, 개발 완료 보고로 표현하지 않는다.

**발표의 한 문장:** 과정과 수업 일정에 따라 반복되는 KDT 운영 자료를 연결하고, 매니저가 오늘 확인할 일과 근거를 한 화면에서 보도록 하는 교육 PM 에이전트.

**청중이 발표 후 답할 수 있어야 하는 질문**

1. 매니저의 어떤 반복 업무와 판단을 돕는가?
2. 설문, 강사 준비, 출결, 운영 사건은 어디서 들어오고 어떻게 연결되는가?
3. 에이전트가 처리하는 일과 사람이 계속 맡는 일은 무엇인가?
4. 현재 확인한 사실과 앞으로 검증해야 할 연결은 무엇인가?
5. KDT 한 기수의 첫 POC는 어디까지인가? 워크샵에서 무엇을 정해야 하는가?

## 1. 워크샵에 넣을 기능과 비중

## 2. 대표님·이사님이 이해할 설명 구조

기능명보다 **업무 장면**을 먼저 보여준다. 동일한 합성 사례인 `KDT A기수 / 강사 A / 수강생 A / 프로젝트 B팀`을 끝까지 사용하되, 서로 관련 없는 사건을 인과관계로 묶지 않는다.

| 설명 순서 | 청중이 볼 것 | 발표자가 말할 핵심 |
|---|---|---|
| 오늘의 업무 | 일정과 할 일 | “오늘 누가 수업하고 무엇이 준비·수집·확인 대기인지 먼저 봅니다.” |
| 연결되는 자료 | Excel·Forms·출결 원천 | “같은 기수·회차·사람에 맞춰 원천과 수집 시점을 연결합니다.” |
| 처리 방식 | 검증·집계·요약·대기 | “숫자는 코드로 계산하고, 주관식과 사건의 맥락을 AI가 정리합니다.” |
| 사람의 조치 | 근거→담당자 확인→처리 기록 | “AI가 결론을 확정하거나 공식 판정을 대신하지 않습니다.” |
| 첫 구현 | 한 기수 파일 기반 POC | “입력·집계·근거·오류 표시를 작은 범위에서 먼저 확인합니다.” |

각 기능 설명에는 최소한 **입력, 처리, 화면 결과, 사람 역할, 실패했을 때 상태**가 들어가야 한다. 장표에는 그중 하나만 크게 보여주고 나머지는 발표자가 말한다. `AI가 알아서` 같은 표현은 쓰지 않는다. 기술 제품명은 연결 구조를 설명하는 장에서만 필요 최소한으로 사용한다.

## 3. 발표에서 오해를 막는 상태·용어 기준

| 표시 | 정확한 뜻 | 사용 위치 |
|---|---|---|
| 확인 사실 | 계정·구독·일부 관리 화면과 자료 구조를 당시 조회한 기록 | 환경 확인 장표. 확인일 표시 |
| 설계안 | 동작, 데이터, 권한, 예외 처리를 문서로 정의함 | 기능·아키텍처 설명 |
| 화면 구상 | 아직 실제 운영 데이터를 연결하지 않은 인터페이스 | 대시보드와 상세 화면 |
| 예시 데이터 | 설명을 위한 합성 기수·수치·인물 | 모든 샘플 표·그래프 |
| 첫 POC 제안 | 한 기수 파일로 입력→검증→집계→화면을 검증할 범위 | 구현 단계 |
| 연동 검증 필요 | 권한·로그인·실제 파일·API·화면 절차의 성공이 아직 확인되지 않음 | Teams·Outlook·LMS·실행기 연결 |
| 추후 후보 | 현재 첫 범위 밖이며 별도 조건 확인이 필요한 기능 | Forms 전 과정 자동화, 단위기간 서류 패키지 등 |

발표 중 반드시 지킬 구분:

- **저장된 일정표를 읽는 설계**와 **실제 Teams 채널 수업 생성·회의 링크 확인**은 다르다. 후자는 실제 환경 검증이 필요하다.
- **Forms 링크 안내**와 **Forms 생성·문항 검수·게시**는 다르다. 현재 설계에서 게시와 응답 Excel 다운로드는 사람 업무다. Excel은 다운로드 시점의 사본이다.
- **설문 점수·응답률 계산**은 SQL/코드, **주관식 요약**은 AI, **개선 결정**은 매니저 역할이다. 익명 응답을 특정 학생 출결에 연결하지 않는다.
- **LMS 입퇴실 조회**와 **호명·중간출결·Teams 3종 파일 종합**은 별도 흐름이다. LMS를 종합 사이트의 네 번째 입력 파일처럼 그리지 않는다.
- **확정된 LMS 반려 사유 안내**와 **신규 증빙의 1차 판독**은 다르다. 신규 증빙의 최종 승인·반려와 사유는 매니저가 결정한다.
- **알림 발송**은 실제 서류 제출·업무 완료의 증거가 아니다. 대기·성공·실패·결과 불명을 따로 표시한다.
- **운영 사건 탐지**는 수강생의 태도·감정·신고 의도 판정이 아니다. 영상에서 카메라 꺼짐·졸음 자동 판정, 하위 Top 3와 자동 경고를 내세우지 않는다.
- **비용 조회값**도 청구 전 추정일 수 있다. Azure 조회 비용과 아직 반영되지 않은 사용 추정을 중복 합산하지 않는다. `2,000`은 통화·기간·관리 대상 확인 전 확정 예산으로 말하지 않는다.
- **환경 조회 기록**은 운영 앱 배포, Teams/LMS 연동 성공, 실제 메시지 발송 성공을 증명하지 않는다. 실환경 사실은 [확인 기록](../../설계보고서/06_실환경_확인기록.md)을 기준으로 한다.
- **K뉴딜 확장**은 구조 재사용 방향이다. 해당 과정의 양식·운영 규칙·권한·연결을 다시 확인해야 한다.

## 4. 실현 가능성과 첫 검증 범위

여기서 `가능`은 설계·구현 경로가 있다는 뜻이며 **실제 운영 성공을 보증하지 않는다**. 난이도는 [구현·검증 계획](../../설계보고서/05_구현_검증_계획.md)의 1~5 기준을 참고한다.

| 단계 | 후보 | 첫 산출물 | 의존 조건·남은 검증 |
|---|---|---|---|
| 첫 POC | 한 기수의 사용 허용된 또는 합성 일정·강의 만족도·출결 샘플 파일 입력 | 원본·수집 시각·양식 버전 검증, 중복 제거, 응답률·출결 상충 집계, 근거가 달린 요약, 간단한 화면 | 양식과 식별키 확정. 파일 기반 결과를 실제 Teams/LMS 자동 수집으로 표현하지 않음 |
| 연결 검증 | 파일 다운로드, 담당자 안내, 월별 채널 수업·Outlook 연결 중 실제 한 흐름 | 권한·대상·실행 결과·실패 상태 기록 | 팀·채널·파일의 실제 ID, 정책·동의·라이선스, 회의 링크와 수신자 확인 |
| 운영 확장 | 일별 강사 준비·설문·업무 대기, LMS 조회, 3종 출결 종합 | 반복 실행과 예외 처리 | 사이트 로그인·MFA·화면 변화, 원천 대조, 공식 승인 절차, 민감 자료 권한 |
| 뒤 단계 | 영상 관찰, 저화질 증빙 판독, 새로운 사이트 탐색, 프로젝트 전용 진행 화면 | 별도 검증 설계 | 데이터 품질·오판·사람 개입률·비용, 프로젝트 입력 주체와 진행 기준 |

첫 POC의 통과 기준은 **원본과 집계의 일치, 중복 방지, 누락·오류의 가시화, AI 요약의 근거 추적, 사람 수정의 기록**이다. 작업 시간·사용량·정확도는 측정하되 임의의 성공률·절감 시간을 슬라이드에 쓰지 않는다. 첫 범위의 `만족도·출결`은 입력과 비교 대상으로 제안한 것이며, 실제 자료 사용은 허용 범위를 확인한다.

### 기술 구조를 설명하는 가장 짧은 방식

교육 Teams와 직원 Outlook 등 기존 업무 환경을 허용된 권한으로 연결하고, Azure 쪽 앱·DB·예약 실행기가 상태와 근거를 관리한다. API·파일 처리로 가능한 업무를 우선 연결하며, 채널 수업 생성이나 일부 LMS 작업처럼 화면 조작이 필요한 곳은 검증된 절차와 완료 검사로 다룬다. 화면이나 로그인 정책이 바뀌면 확인 대기로 남긴다. 새 앱·권한·운영 리소스는 아직 배포 완료로 말하지 않는다. 근거: [공통 아키텍처](../../설계보고서/01_공통_아키텍처.md), [세 계정 연결](../../설계보고서/02_테넌트_연결.md), [컴퓨터 사용 F19](../../설계보고서/기능/F19_컴퓨터유즈_경험메모리.md).

## 5. 워크샵에서 논의할 내용

오전 브리핑은 제안과 경계를 설명하고, 발표 직후 또는 오후에 다음 결정을 요청한다. 장표에는 질문 전체를 싣지 않고 **결정 주제만** 남긴다.

| 우선 | 정해야 할 것 | 이유 | 제안하는 기본 출발점 |
|---|---|---|---|
| 1 | 첫 대상 기수와 사용 허용 자료 | 실제 양식·식별키·권한이 POC 입력을 결정 | KDT 한 기수의 일정·만족도·출결 샘플 |
| 2 | Forms 게시·응답 다운로드·자료 갱신 담당 | 현재 설계의 사람 작업이 실행되지 않으면 집계가 갱신되지 않음 | 담당자와 다운로드 주기 지정 |
| 3 | 강의 설문·운영 설문의 문항과 주기 | 강의는 일별, 운영은 기수당 약 3회가 기본 설계 | 짧은 강의 설문부터 검증, 운영 설문 빈도는 응답 부담을 보고 결정 |
| 4 | 출결 확인 기준과 예외 | 조회 지연·공결·중복 이름을 잘못 안내하지 않기 위해 필요 | 누락 관찰→매니저 확인→공식 판단의 단계 유지 |
| 5 | 업무별 수신자·승인·민감정보 열람 범위 | 안내와 외부 전달의 대상 오류를 막아야 함 | 승인 대상과 자료 종류를 업무별로 지정 |
| 6 | 프로젝트 모니터링의 첫 범위 | 현재는 사건·멘토링 근거가 있고 전용 단계 모델은 없음 | 제출 기한·산출물 상태·멘토링 여부부터 입력 가능성 확인 |
| 7 | 첫 POC 이후 실제 연결을 무엇부터 검증할지 | 모든 테넌트·LMS를 동시에 연결할 필요는 없음 | 실제 자료 한 흐름을 끝까지 검증한 후 확대 |
| 8 | 비용 관리의 대상·통화·기간 | 에이전트 비용과 학생 프로젝트 비용을 섞지 않기 위해 필요 | AI PM 전용 범위부터 조회·추정 구분 |

## 6. 본편 36장 구성과 시간

**36장은 30분 브리핑용이다.** 화면 설명은 한 장당 평균 50초이며, 몇 장은 20~30초에 넘긴다. 장표의 글자는 짧은 제목과 라벨 중심으로 유지하고 설명은 발표자가 한다. 시간이 밀리면 23~24, 27~28장의 보조 사례를 빠르게 넘기되 29~36장의 결과·검증·논의는 남긴다.

| 파트 | 페이지 | 장수 | 시간 | 질문 |
|---|---:|---:|---:|---|
| A. 시작과 목표 | 01~02 | 2 | 1분 30초 | 무엇을 만들려는가? |
| B. 운영의 하루 | 03~06 | 4 | 3분 | 매니저는 무엇을 반복 확인하는가? |
| C. 자료와 연결 | 07~10 | 4 | 3분 30초 | 어떤 자료를 어떻게 믿고 연결하는가? |
| D. 강사·만족도 | 11~15 | 5 | 5분 | 강의 경험을 어떻게 개선 업무로 바꾸는가? |
| E. 출결·학생 지원 | 16~20 | 5 | 5분 | 어떤 기록을 확인하고 누가 판단하는가? |
| F. 반복 업무·프로젝트 | 21~24 | 4 | 3분 30초 | 일정에 따른 업무와 프로젝트 사건을 어떻게 다루는가? |
| G. 대시보드와 판단 | 25~28 | 4 | 3분 | 매니저는 무엇을 한눈에 보고 처리하는가? |
| H. 구현과 첫 POC | 29~32 | 4 | 3분 | 실제로 무엇부터 검증할 것인가? |
| I. 경계와 논의 | 33~36 | 4 | 2분 30초 | 무엇을 결정하면 다음 단계로 갈 수 있는가? |
| **합계** | **01~36** | **36** | **30분** | 발표 직후·오후 논의 별도 |

### A. 시작과 목표 · 01~02

| 장 | 장표의 한 문장 | 화면에 남길 글자 | 넣을 도식·화면 | 발표자가 설명할 내용·상태 |
|---|---|---|---|---|
| 01 | KDT 운영 자료를 연결해 매니저의 판단을 돕는다 | `KDT 교육 PM 에이전트`, `오늘의 운영` | 강사·수강생·수업 상태가 한 화면으로 모이는 **간결한 구성도** | 설계 방향 소개. 완성 제품처럼 보이는 상세 수치 없음 |
| 02 | 첫 적용은 KDT이며 이후 과정에 구조를 재사용한다 | `KDT 한 기수`, `검증`, `확장` | 기수 하나에서 다른 기수와 K뉴딜로 이어지는 단계 도식 | K뉴딜은 규칙·양식 확인 후 적용. 확정 일정 표시 금지 |

### B. 운영의 하루 · 03~06

| 장 | 장표의 한 문장 | 화면에 남길 글자 | 넣을 도식·화면 | 발표자가 설명할 내용·상태 |
|---|---|---|---|---|
| 03 | 매니저는 수업 전후에 같은 자료를 여러 번 확인한다 | `일정`, `준비`, `출결`, `설문` | 수업 전·중·후 **하루 시간축**에 자료를 배치 | 시간이 아니라 확인 대상의 연결 문제를 설명. 절감 시간 수치 금지 |
| 04 | 오늘의 수업은 일정 한 줄에서 시작한다 | `KDT A기수`, `강사 A`, `오늘 수업` | 일정표 한 행을 확대해 수업일·회차·강사·시간 표시 | 복수 강사·시간 분할과 휴강은 검증 대상 |
| 05 | 일정이 바뀌면 연결된 예약과 담당 업무도 다시 확인한다 | `변경`, `재확인`, `대기` | 변경 전후 일정과 영향을 받는 안내·설문 예약을 연결한 **전후 비교도** | 잘못된 대상 발송과 중복 실행을 막는 구조 |
| 06 | 매니저에게는 자동 처리와 사람 작업이 같이 보인다 | `처리 완료`, `사람 작업 대기`, `결과 불명` | 간단한 업무 진척도 목록과 세 가지 상태 | 안내 발송만으로 제출·검수 완료로 취급하지 않음 |

### C. 자료와 연결 · 07~10

| 장 | 장표의 한 문장 | 화면에 남길 글자 | 넣을 도식·화면 | 발표자가 설명할 내용·상태 |
|---|---|---|---|---|
| 07 | 운영 자료는 기수·회차·사람 기준으로 연결한다 | `일정`, `강사 자료`, `설문`, `출결`, `공통 DB` | 4개 입력에서 공통 장부로 들어오는 **관계 도식** | 같은 이름만으로 연결하지 않고 식별키·수집 시각을 사용 |
| 08 | 설문 응답은 Forms에서 사람이 내려받은 Excel로 들어온다 | `Forms`, `Excel 다운로드`, `검증`, `집계` | Forms 화면 조각→Excel 표→집계 결과의 **업무 흐름** | 게시·다운로드는 사람, 파일 검증·집계는 에이전트 |

| 10 | 원천, 버전, 수집 성공 여부가 숫자의 신뢰도를 정한다 | `원천`, `양식 버전`, `수집 시각`, `오류` | 하나의 집계 카드 옆에 데이터 상태를 보이는 **근거 확대 화면** | 데이터 없음·오래됨·실패를 `0`이나 정상으로 표시하지 않음 |

| 15 | 반복 의견은 강사 준비 개선과 후속 확인으로 이어진다 | `반복 의견`, `원문 근거`, `후속 확인` | 주관식 의견→요약→매니저 검토→다음 회차 확인 **근거 흐름** | AI는 의견 요약, 개선 결정은 매니저. 강사 상세 표현은 화면 구상 |

### F. 반복 업무·프로젝트 · 21~24

| 25 | 매니저 화면은 오늘의 수업과 확인할 일을 먼저 보여준다 | `오늘의 운영`, `확인할 업무` | F21 기준 **대시보드 전체 화면**을 장표 대부분에 배치 | `화면 구상·예시 데이터` 표기. 실제 제품 연결처럼 소개하지 않음 |
| 26 | 카드의 숫자를 누르면 원천과 실행 상태로 내려간다 | `원천`, `수집 시각`, `실행 결과` | 25장 화면의 한 영역을 **확대**해 근거·버전·실패 표시 | 최신성·권한·결과 불명을 감추지 않음 |
| 27 | AI 요약은 확인된 사실과 추정을 나눠 보여준다 | `확인된 사실`, `요약`, `확인 필요` | 설문 주관식 원문과 F09 사건 요약의 **근거 연결 화면** | F06·F09 범위만. 여러 영역 통합 인사이트는 향후 별도 설계 |
| 28 | 에이전트 비용도 조회값과 미반영 추정을 나눠 본다 | `조회 비용`, `사용 추정`, `대조 상태` | F18의 **두 금액·상태 비교 차트** 또는 작은 비용 화면 | 통화·기간·ACR 대상 미확정, 이중 합산 금지 |

### H. 구현과 첫 POC · 29~32

| 장 | 장표의 한 문장 | 화면에 남길 글자 | 넣을 도식·화면 | 발표자가 설명할 내용·상태 |
|---|---|---|---|---|
| 29 | 기존 교육·직원 환경을 허용된 권한으로 연결한다 | `교육 Teams`, `직원 Outlook`, `Azure` | 세 역할과 앱·DB·예약 실행기의 **단순 연결도** | 계정을 하나로 합치는 설계 아님. 실제 연결은 검증 필요 |
| 30 | 자동화 방식은 API·파일 처리와 검증된 화면 절차로 나뉜다 | `API·파일`, `화면 절차`, `완료 검사` | 업무 예시별 실행 방식 **2열 비교 도식** | 로그인 만료·화면 변경은 확인 대기. 자동 학습·권한 우회 약속 금지 |
| 31 | 첫 POC는 한 기수의 파일 입력부터 결과 화면까지다 | `파일 입력`, `검증·집계`, `근거 요약`, `화면` | 실제 연결 단계와 분리한 **첫 POC 경계선 도식** | Teams·LMS 자동 수집까지 성공했다고 표현하지 않음 |
| 32 | POC는 보기 좋은 화면보다 원본과 결과의 일치를 확인한다 | `원본 일치`, `중복 방지`, `오류 표시`, `근거` | 입력 행→집계값→근거 링크를 대조하는 **검증 표** | 정확도·시간·비용은 측정 예정. 목표 수치 임의 제시 금지 |

### I. 경계와 논의 · 33~36

| 장 | 장표의 한 문장 | 화면에 남길 글자 | 넣을 도식·화면 | 발표자가 설명할 내용·상태 |
|---|---|---|---|---|
| 33 | 지금 확인된 것은 환경 일부이고 업무 연동은 검증해야 한다 | `확인 사실`, `설계안`, `연동 검증 필요` | 세 상태를 나란히 놓은 **증거 수준표** | 06 확인 기록 날짜·범위만 표시. 배포·발송 완료 주장 금지 |
| 34 | 운영 결정은 사람이 맡고 실패는 화면에 남긴다 | `사람 승인`, `권한`, `실패·재처리` | 자동 처리와 사람 승인, 오류 분기를 보이는 **통제 흐름** | 개인정보·의료 서류·외부 전달의 확인 절차 |
| 35 | 다음 단계의 우선순위는 첫 대상과 운영 기준에 달려 있다 | `첫 대상`, `설문 주기`, `출결 기준`, `프로젝트 범위` | 워크샵 논의 의제를 4개 영역으로 정리한 **의사결정 화면** | 프로젝트 전용 기능과 통합 인사이트는 합의 전 확정 기능 아님 |
| 36 | KDT 한 기수에서 확인하고 결과를 보고 확장한다 | `KDT 우선`, `담당 역할`, `다음 검증` | KDT 한 기수→실제 연결 하나→다른 기수/과정 **단계 도식** | 논의로 넘기는 마무리. 날짜·예산·완료율 약속 없음 |

## 7. 시각 자료 제작 원칙

- **LLM 이미지 생성 도구로 만든 이미지·삽화는 사용하지 않는다.** 사람·강사·학생 상황을 그린 생성 삽화도 넣지 않는다.
- 실제로 제작할 시각물은 **HTML/CSS 인터페이스 화면, 일정·업무 흐름 도식, 근거가 있는 표와 그래프**다. 최종 PPT에는 완성된 화면 캡처 또는 직접 만든 도식을 배치한다.
- 한 페이지에 한 질문과 한 주된 시각물만 둔다. 도식의 화살표는 실제 데이터·업무 흐름을 뜻할 때만 사용한다.
- 그래프는 분모·기간·척도·응답 수·수집 시각을 함께 표시한다. 샘플 수치는 반드시 `예시 데이터`로 표시한다. 실측 효과·성공률 그래프는 검증 전에는 만들지 않는다.
- 자료나 권한을 모르는 구간은 선을 끊거나 `연동 검증 필요`로 표시한다. 실패·결과 불명·사람 작업 대기를 녹색 완료처럼 보이게 하지 않는다.
- 출결, 강사 피드백, 프로젝트 사건은 같은 합성 기수로 설명하지만 서로 원인이라고 단정하지 않는다. 익명 설문과 특정 학생 신원은 연결하지 않는다.
- 본편에 세부 DB 컬럼표·가격표·리소스 SKU·계정 ID·민감한 원문은 넣지 않는다. 필요한 정보는 질문을 받았을 때 설계보고서에서 확인한다.

## 8. 발표 제작 전 준비할 근거와 데이터

| 준비물 | 필요한 이유 | 준비 기준 |
|---|---|---|
| 동일 기수의 합성 사례 | 36장이 한 운영 흐름처럼 이어지게 하기 위함 | `KDT A기수 / 강사 A / 수강생 A / 프로젝트 B팀`으로 통일 |
| 일정·설문·출결 샘플 행 | 화면의 수치·상태를 앞뒤 장표에서 일치시키기 위함 | [데이터 컬럼·엑셀 양식](../../설계보고서/09_데이터_컬럼_엑셀양식.md) 기준으로 생성·대조 |
| 기능별 상태 근거 | `확인 사실`과 `설계`를 섞지 않기 위함 | [실환경 확인 기록](../../설계보고서/06_실환경_확인기록.md)과 [연결 체크리스트](../../설계보고서/07_세계정_연결권한_체크리스트.md) 대조 |
| 첫 POC 입력·출력 예시 | 31~32장의 실현 가능성을 구체적으로 보여주기 위함 | 파일 기반 처리의 범위와 실패 예시를 함께 준비 |
| PPT 양식 | 최종 글꼴·색·여백·화면 비율을 맞추기 위함 | 양식 확인 후 장표를 배치. 이 문서는 내용과 시각 구조의 기준 |

## 9. 최종 검토 체크

1. 36장 모두 한 문장으로 목적을 말할 수 있는가?
2. 각 수치와 상태에 `예시 데이터`, `화면 구상`, `확인 사실`, `연동 검증 필요` 중 적절한 표시가 있는가?
3. 수집→검증→요약→매니저 판단의 흐름에서 사람 작업이 빠지지 않았는가?
4. Forms Excel 사본, 출결 3종과 LMS 별도 대조, 신규 증빙 1차 판독과 최종 승인 구분이 유지되는가?
5. 프로젝트 전용 진행 화면·통합 운영 인사이트를 기존 기능이나 구현 완료로 보이게 하지 않았는가?
6. 개인정보·의료 원문·실제 계정 식별 정보가 본편에 노출되지 않는가?
7. 경영진이 30분 뒤 첫 적용 대상, 담당 역할, 운영 기준, 다음 검증 항목을 논의할 수 있는가?
