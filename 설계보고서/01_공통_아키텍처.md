# 공통 아키텍처

[문서 목록](00_보고서_안내.md)

기준일: 2026-10-28

**참고 설계:** 자료의 해석 기준을 따릅니다. 모델은 실제 테스트·운영에서 품질과 비용을 보고 교체하며, 리소스 생성·데이터 저장·AI 처리 위치는 상황별로 선택·변경합니다. 예산·일정·리전·지원 형식을 확정 약속으로 해석하지 않습니다.

## 1. 한 문장 설명

**AI는 업무를 이해하는 담당자, 예약 시스템은 시계를 보는 담당자, 실행 도구는 손발, DB는 공동 업무 장부입니다.** 역할을 분리해 AI 대화가 끝나거나 특정 사이트가 고장 나도 다른 업무를 계속합니다.



**일정 운영 기준(사용자 설명·캘린더 기준): 한 기수는 수업일마다 하루 수업 일정 1개를 운영하고, 같은 날짜에 여러 기수가 각각의 강의를 동시에 운영합니다.** 기수별 달력에는 해당 기수의 일별 수업 일정 하나가 보이며, 전체 달력의 같은 날짜에 보이는 여러 강의는 서로 다른 기수의 일정입니다. 강사·과목은 날짜에 따라 바뀔 수 있고, 공동 멘토링의 복수 담당자도 하루 일정 하나에 연결합니다. 오전·오후 출결이나 분할 녹화는 같은 하루 강의의 내부 구간입니다.

**운영 단위:** `course_id`는 KDT 과정의 한 기수, `teaching_unit_id`는 그 안에서 며칠에 걸쳐 진행되는 한 강의, `session_id`는 하루 수업 일정입니다. 강의 단위에는 시작일·종료일·강사/보조강사·관련 일별 일정을 명시합니다. 같은 과목명·강사명이나 날짜만으로 강의 경계를 추정하지 않으며, 한 강의가 월을 넘어도 같은 ID를 유지합니다.

**강의 준비 소통:** 시작 D-7에 강사·보조강사·회사 직원 그룹 채팅을 준비하고 승인 대사를 발송합니다. 기존 수업 채널·회의 생성과 별도의 업무입니다([F04](02_과정_설정과_일정_운영.md#f04)).

## 2. 고정할 구조와 늘릴 부분

| 구역 | 하는 일 | 과정 증가 시 대응 |
|---|---|---|
| 운영 화면 | 과정·학생·일정·승인·사람이 할 일·진척도 | 같은 화면에 과정 추가, 역할별 조회 |
| 업무 API | 화면·파일 변경·외부 요청 검증 | 요청 처리 인스턴스 증가 |
| AI PM | 일정 해석·검색·문항 초안·요약 | 모델 한도·동시 호출량 조절 |
| 규칙·예약 | 기수별 하루 수업 일정 1개의 시작·종료와 날짜별 강사·과목 기준 업무 시각 계산 | 과정별 규칙·예약 데이터 증가 |
| 작업 대기열 | 몰린 업무 대기·실패 분리 | 작업 종류·계정별 대기열 분리 |
| 실행기 | Teams 발송·일정 화면 조작·파일 처리·LMS 조회 | 실행기 확장, 같은 계정 작업 직렬화 |
| 공동 DB | 학생·강사 배정·설정·승인·실행 이력 | 인덱스·용량·읽기 성능 조절 |
| 자료 저장소 | 원본·결과 파일·허용된 증거 | 보관·삭제 정책 적용 |

기능마다 AI·DB·예약기를 별도로 만들지 않습니다.

## 3. 실제 처리 예시

기본 규칙은 한 번 등록하고 반복 업무는 일정에 맞춰 실행합니다. **기수 내 강의 시작 1주일 전에는 강사·보조강사·회사 직원 단체 채팅과 준비 대사를, 며칠간 진행된 강의 종료 후에는 객관식 2개·주관식 1개 만족도를 실행**합니다. 최초 규칙 승인·중요 결정·인증/예외와 퀴즈 검수 등 사람 작업은 별도로 표시합니다.

1. **일정표 읽기:** 매니저·강사가 Teams/SharePoint 공유 엑셀을 직접 편집·저장합니다. 폴더 구조 예시의 운영 채널 루트 시간표와 수강생 `일반 / 02. 시간표` 중 기준 원본과 배포본 관계를 지정하고, 에이전트는 기준 파일의 버전을 확인해 다운로드·파싱합니다. 수업 편성은 일정표, 직원 근무 일정은 Outlook을 기준으로 하며 원본 셀을 직접 덮어쓰지 않습니다.
2. **회차·강사 검증:** 한 기수의 하루 강의를 하나의 회차 ID로 연결하고 기수·수업일·시작/종료·담당 강사를 검증합니다. 권진욱 → 강명호 → 인선미처럼 날짜별 강사 교체를 반영하며, 공동 멘토링 담당자는 같은 하루 일정에 복수 배정합니다. 같은 날짜의 다른 기수 강의는 별도 회차·대상으로 처리합니다. 시간 정보가 없으면 사람이 보완합니다.
3. **1개월 단위 Teams 수업 생성:** 현재 매니저가 일일이 만드는 채널 수업 일정을 **Teams 웹 일정의 컴퓨터 사용**으로 생성·수정합니다. 대상 팀·채널·주최자·수업일을 확인하고 해당 월만 발행합니다. 다음 달은 DB에서 대기합니다. 실제 생성된 회의 링크를 Graph로 직원 Outlook 일정에 반영하며 별도의 일반 온라인 회의를 중복 생성하지 않습니다.
4. **강사 접근 준비:** 기존 가입과 채널 유형을 조회합니다. 표준 채널은 팀 멤버십, 비공개·공유 채널은 별도 가입 조건을 따릅니다. 현재 공통 팀에서는 다른 기수 자료가 보일 수 있습니다. 실제 구조와 권한 영향을 확인한 뒤 사전 승인된 구성원 추가만 자동 수행하고, 미확정이면 매니저 확인 대기로 둡니다.
5. **반복 업무 예약:** 수업 전날 해당 강사에게 교안·출석부·중간평가 확인을 요청합니다. 휴강·방학에는 관련 예약을 생략하고, 실행 직전 일정·강사 교체·기제출 여부를 다시 확인합니다.
6. **오전 자료로 오후 퀴즈 준비:** 하루 3~4개로 나뉘어 저장되는 녹화 중 **처음 저장 완료된 오전 구간**과 당일 교안을 분석합니다. 오후 배포 전 강사 검수·사람의 Forms 게시·링크 등록을 기다립니다. 파일 저장·처리가 늦으면 확인된 교안·진도만으로 초안을 만들고 근거 범위를 표시하거나, 진도도 불명확하면 생성 대기로 둡니다.
7. **역할별 실행·보관:** 학생 안내·강사 소통·내부 보고는 11 문서의 Teams 역할 매핑을 따릅니다. 수강생 파일 공유는 `일반` 안에서만 하며 `05. 강의자료`·`Recordings`를 참고합니다. 강사팀 `출석부`의 호명 원본을 읽고, 내부 3종 원본·종합본은 **운영 채널 `출석부 / 월 / 주차 / 일자`**에 별도 파일로 보관합니다. 강의 단위 종료 Forms 응답은 Logic Apps → Service Bus → DB로 수집하고 집계 Excel·요약을 운영 채널 `중간평가 및 설문`에 별도 저장합니다. 참가 신청·동의서 등 다른 목적 양식의 다운로드 결과·강의 단위 종료 설문 복구 사본은 원천과 시각을 구분합니다. 외부 출석 업무는 기관·자료 버전·대상을 지정한 요청과 매니저 승인이 있을 때만 **출석 관리 팀**으로 전달합니다.
8. **강의 단위 종료별 1회 만족도:** `course_id + teaching_unit_id`별 승인 템플릿(선택형 2개·주관식 1개)을 F19로 준비하고 양식/문항·응답 링크·R19 수집 연결을 등록합니다. 해당 강의 마지막 수업 종료 확인 후 안내하고, 응답 검증·집계·요약·별도 결과 저장을 실행합니다. 기수 전체가 계속 운영 중이어도 종료한 강의의 설문은 실행합니다([F06](05_강의_단위별_만족도.md#f06)).
9. **사전 출결 일정 대조:** 기수별 `01. 출결 게시판`의 지각·조퇴·외출 예정과 변경/취소를 LMS 입퇴실 확인 전에 수집합니다. 신고한 입실·퇴실·복귀 시각과 실제 기록·호명 출석부를 대조해 학생별 확인 예약과 안내를 갱신합니다. 접수된 신고는 일반 미클릭 독촉 방지에 반영하고 공식 인정·정정은 별도 상태로 둡니다. 게시판 수집 실패를 신고 없음으로 보지 않습니다([F15](06_출결과_증빙_처리.md#f15)).
10. **진척도 집계:** 파일 수집·일정 발행·사람의 작업·승인·외부 전달을 구분해 직원 대시보드에 표시합니다. 알림 발송을 실제 업무 완료로 간주하지 않습니다.

**구조 예시와 실제 연결의 구분:** 사용자 제공 구조를 자료 역할·경로의 참고 기준으로 반영했습니다. 날짜·강사명·파일명·세부 구성은 테스트 및 운영을 하면서 바꿀 수도 있습니다. 기수별 운영 채널의 소속 팀, 실제 채널 유형·사이트·드라이브·폴더 ID·권한은 별도 확인하며 미확인 연결은 보관 대기로 표시합니다. 폴더명만으로 임의 저장·외부 전달하지 않습니다.

## 4. Azure 배치 기준안

운영 인프라는 `@msacademy` 계정으로 접근하는 회사 **엘릭서 구독**(`msaischool.onmicrosoft.com`)에 둡니다. `@elixirr`·`@dataschool`에는 연결 앱·동의·Teams 앱을 구성합니다. 기존 리소스는 임의 변경하지 않으며 개발/운영의 권한·키·데이터·수신자를 분리합니다.

- **웹/API:** Container Apps. 직원 로그인은 `@elixirr`, 교육 Teams 연결은 `@dataschool`.
- **Forms 수집:** Logic Apps Consumption + Forms API 연결. 교육 조직 계정의 최초 OAuth 인증과 양식별 트리거 연결이 필요합니다. 설문 생성은 F19 브라우저 절차, 응답 수집은 공식 커넥터로 구분합니다.
- **AI:** Foundry Agent Service와 작업별 배포 모델. 권한·규칙의 최종 검사는 서버 코드.
- **예약:** Functions(Flex Consumption)의 Durable Functions + Durable Task Scheduler.
- **작업 전달:** Service Bus. 발송·문서·웹/PC 작업 분리.
- **운영 DB·검색:** PostgreSQL Flexible Server + `vector`, 운영용 General Purpose 2 vCore부터.
- **파일:** 기존 SharePoint/Teams 원본을 우선 사용하고, 필요한 처리 사본·증거는 Blob. Drive API로 저장된 파일을 읽고 별도 결과 파일을 쓰며 Excel 셀·Word 원문은 사람이 편집.
- **웹 자동화:** 검증된 Playwright 절차 또는 Foundry Browser Automation. Teams 채널 수업 생성·참석 CSV 다운로드·LMS 조회에 사용.
- **문서·영상 추출:** Content Understanding 및 한글 `.hwp`/`.hwpx` 전처리. 형식·분량·화질에 따라 실패·누락을 표시하고 사람 확인.
- **비밀·감시:** Key Vault, Managed Identity, Monitor/Application Insights.
- **화면 예외:** computer use는 선택 경로. 리전은 서비스·모델 제공 여부·쿼터·정책·지연·비용에 따라 실제 테스트·운영에서 선택·변경합니다. 조사 당시 지역별 제공 이력은 실환경 확인 절을 참고하며 특정 지역에 영구 고정하지 않습니다.

리소스별 생성 위치·계정·SKU·상태·선정 이유는 [Azure 리소스](#azure-resources) 명세를 따릅니다. 리소스 그룹 분리는 구독 전체 장애·청구·상위 정책까지 분리하지는 않습니다.

## 5. 대기열과 예약기가 둘 다 필요한 이유

- **Durable Functions:** 시각 대기·사람 승인·재안내·복구 순서를 기억합니다.
- **Service Bus:** 지금 몰린 작업을 실행기 처리량에 맞게 전달합니다.
- **PostgreSQL:** 실제 업무·승인·결과의 원본입니다. 예약기 이력으로 업무 장부를 대체하지 않습니다.

업무 변경과 발행 예정 항목은 같은 DB 트랜잭션에 저장합니다. 별도 전달기가 대기열에 보내고 실행 키로 중복을 막는 outbox 방식을 사용합니다.

## 6. 업무가 몰려도 섞이지 않게 하기

1. 작업마다 `organization_id`, `course_id`, `connection_id`, `rule_version`, `run_id`를 기록합니다.
2. 과정별 우선순위와 동시 실행 한도를 둡니다.
3. 같은 사이트·계정의 로그인 세션은 잠금으로 직렬화합니다.
4. Graph·Teams 과다 요청은 지정된 대기시간을 지킵니다.
5. 반복 실패는 해당 연결만 중단하고 담당자에게 알립니다.
6. 모델에는 해당 업무의 허용된 자료만 전달합니다. 앱에 넓은 사이트 권한이 있어도 업무별 파일 범위를 서버에서 제한합니다.

처리량은 같은 시각의 작업 수와 작업당 시간·계정별 동시성으로 산정합니다. 측정 없이 무제한 확장이나 확정 성능을 주장하지 않습니다.

## 7. 설정 변경과 새 개발의 구분

| 변경 | 처리 |
|---|---|
| 기존 기능의 시각·대상·재안내·기간 변경 | 설정 버전 변경과 예약 재계산 |
| 체크리스트 항목·엑셀 컬럼 변경 | 양식 버전·컬럼 매핑 검사, 모호한 항목은 사람 확인 |
| 등록된 도구로 새 업무 조합 | 허용 동작·의존성 검증 |
| 새 사이트·미지원 파일 형식·새 권한 | 연결·파서·절차 개발 또는 관리자 설정 후 배포 전 확인 |
| 운영 코드 교체 | 개발 환경 작업·사람 검토·승인 후 배포 |

# 세 테넌트를 연결하는 방법

[문서 목록](00_보고서_안내.md)

[공통 구조](#architecture)

이 문서의 연결 방식은 공통 참고 기준을 따릅니다. 모델·리전·구현 일정은 테스트·운영에서 변경할 수 있으며, 실제 계정·권한 확인값의 주력 기록은 11 문서의 실환경 확인 절입니다.

## 1. 쉽게 설명하면: 세 사무실을 연결하는 업무 데스크

`@msacademy`, `@elixirr`, `@dataschool`을 서로 다른 출입증을 쓰는 사무실이라고 생각하면 됩니다. 벽을 없애고 직원과 학생의 권한을 섞는 것이 아니라, 중앙 AI가 **각 사무실에서 허용한 업무용 출입증**으로 필요한 일만 합니다.



| 사무실 | 남겨둘 역할 | 중앙 시스템이 연결할 것 |
|---|---|---|
| `@msacademy` | Azure 운영·실습 | 운영 앱·DB·AI, 허용 구독의 사용량 |
| `@elixirr` | 직원 전용 업무 | Outlook 일정·업무 메일·직원 Teams |
| `@dataschool` | 교육 운영 | 강의 회의·학생/강사 Teams·교육 자료 |

**`@elixirr`에 Azure 리소스를 만들 필요는 없습니다.** 해당 조직의 일정과 Teams에 접근할 앱 권한만 준비할 수 있습니다.

Teams 자료는 사용자 제공 폴더 구조의 **수강생 팀 `일반`·기수별 운영 채널·강사팀**으로 나눠 연결합니다. 이는 세 테넌트와 다른 구분이며, 세 자료 영역마다 새 테넌트를 만드는 설계가 아닙니다. 수강생 파일은 `일반`에서만 공유하고, 운영 채널·강사팀 자료를 자동 공개하지 않습니다.

실제 Azure 화면에서는 회사 **엘릭서 구독**이 `msaischool.onmicrosoft.com` 디렉터리에 연결되어 있습니다. “엘릭서 구독”이라는 청구/관리 이름과 “`@elixirr` 회사 계정의 테넌트”는 다른 개념입니다.

## 2. 무엇을 합치고, 무엇을 분리하는가

- 합치는 것: 운영 화면, 과정·학생 연결 정보, 실행 요청, 진행 상태, 직원용 보고.
- 분리하는 것: 로그인 계정, 테넌트별 권한, 강의/사내 회의, 비밀값, 민감 자료 열람 범위.
- 복사하지 않는 것: 회사 전체 메일·대화, 다른 과정 자료, 권한 없는 녹화본.

같은 사람이 여러 계정을 갖더라도 내부 인물 번호와 각 조직의 계정 번호를 연결합니다. 메일 표시 이름이나 학생 닉네임만으로 자동 결합하지 않습니다.

## 3. 기본 연결 방식

테넌트마다 필요한 연결 앱을 등록하고 동일한 연결 프로그램에 설정합니다.

```text
중앙 업무: AI 5기 강사에게 안내
  → 대상 과정의 연결 설정 조회
  → @dataschool 테넌트용 인증 토큰 발급
  → 허용된 Teams 대화에 안내
  → 결과만 공통 DB에 저장
  → @elixirr 직원 화면에서 확인
```

- `@elixirr`: 직원 일정·메일용 앱. 직원 Teams 봇 연결은 해당 조직의 설치·동의 절차를 따릅니다.
- `@dataschool`: 교육 메시지·문서용 앱과 Teams 앱. 채널 수업 일정은 별도로 허용된 Teams 웹 실행 계정·로그인 정책을 확인합니다.
- `@msacademy`: 운영 프로그램의 관리 ID를 우선 사용합니다.
- **강의 단위 종료 만족도 Forms:** Azure Logic Apps Consumption은 엘릭서 구독에 배치하고 Forms 연결은 권한 있는 `@dataschool` 조직 계정으로 최초 OAuth 인증합니다. Graph 앱 동의·관리 ID를 Forms 연결 인증과 혼동하지 않습니다. 설문 복제·링크 확보는 F19 브라우저 절차, 응답은 양식별 커넥터 트리거로 수집합니다. 다른 테넌트 구독에서의 API 연결·정책·인증 갱신은 실제 검증합니다([F06](05_강의_단위별_만족도.md#f06)).
- 서버는 연결 대상 테넌트를 명시해 토큰을 발급받습니다. 세 조직의 권한이 합쳐진 만능 토큰을 만들지 않습니다.
- 인증서/지원되는 연합 자격 증명을 우선 검토하고, 비밀값은 Key Vault에서 관리합니다. 운영자 비밀번호를 상시 보관해 대신 로그인하는 방식을 Graph의 기본 인증으로 사용하지 않습니다.

테넌트가 계속 추가될 경우, 연결 앱을 멀티테넌트 앱으로 전환해 설치 절차를 표준화할 수 있습니다. 이 경우에도 각 조직의 서비스 주체 생성·관리자 동의는 필요합니다.

## 4. 세 조직에 직접 설정할 내용 (관리자 권한 확보 완료)

세 계정(`@msacademy`, `@elixirr`, `@dataschool`) 모두 각 조직의 **Global Administrator** 권한이 확인되었으므로, 별도의 타 관리자 승인 대기 없이 아래 설정을 직접 구성하고 검증합니다.

| 대상 | 직접 설정할 내용 | 확인할 실제 동작 |
|---|---|---|
| `@msacademy` Azure | 운영 구독·배포 권한·정책·모델별 쿼터(06 CLI 조회 완료) | 운영 앱 배포 가능 범위, 모델/리전 목록 |
| `@elixirr` Entra/Exchange | 앱 등록 및 관리자 동의, 일정·발신 메일함 범위 지정 | 지정 일정 읽기/쓰기, 지정 발신자 배포 전 확인 |
| `@elixirr` Teams | 직원용 앱 설치·공지 채널 지정 | 운영국 경보·승인 카드 수신 |
| `@dataschool` Entra/Teams | 교육용 앱 동의·팀/채팅 설치·주최자 정책 | 메시지 수신·발송, 교육 회의·자료 접근 |
| `@dataschool` Forms / Azure Logic Apps 연결 | 강의 단위 종료 시 1회 3항목 설문의 소유 계정·양식별 연결·조직 계정 OAuth·브라우저 세션 준비 | 같은 날 서로 다른 두 기수의 자동 준비·수집·집계, 익명 설정, 연결 만료 복구 |
| `@dataschool` SharePoint | 지정 교육 사이트 권한 | 교안·녹화·서류의 허용 범위 읽기/쓰기 |

**Azure 구독 Owner와 조직별 Entra Global Administrator는 서로 다른 테넌트 권한입니다.** 현재 `@msacademy`는 엘릭서 구독 Owner이자 해당 디렉터리의 Global Administrator이며, `@elixirr`와 `@dataschool` 역시 각 조직의 Global Administrator임이 확인되었습니다([실환경 확인 기록](11_구현_검증과_실환경.md#environment-observations) 참조). 단, 세 조직 모두 최고 관리자 권한을 보유하고 있더라도 에이전트에는 관리자 계정을 그대로 쓰지 않고 앱별 최소 권한만 부여합니다.

## 5. 권한 설계

| 작업 | 설계 기준 |
|---|---|
| 직원 캘린더 | Exchange Application RBAC로 필요한 메일함·일정 범위 설정. 엑셀 일정표 기반 **1개월 단위 수업 이벤트 일괄 생성/갱신** 및 범위 밖 접근 차단 확인 |
| 메일 발송 | 필요한 발신 메일함으로 제한. 메일 읽기 권한과 별도로 검토 |
| Teams 메시지 읽기 | 팀/채팅별 RSC가 지원하는 작업은 해당 범위 동의 사용. 채널·그룹채팅·회의채팅의 API와 권한을 구분 |
| Teams 알림 | 설치된 Teams 앱/봇의 대화 컨텍스트로 발송. Graph 일반 앱 권한이 모든 메시지 발송을 허용한다고 가정하지 않음 |
| 강사 구성원 관리 | 표준 채널은 팀 가입, 비공개·공유 채널은 유형별 가입 조건 확인. 공통 팀의 다른 기수 자료 열람 가능성을 기록하고 실제 구조 확인 후 사전 승인된 추가만 자동 수행. 기존 권한은 임의 회수하지 않음 |
| 교육 회의 생성 | 실제 채널 수업은 Teams 웹 일정의 컴퓨터 사용으로 1개월치 생성·수정. 일반 온라인 회의를 만들고 채널에 링크만 게시하는 것과 구분 |
| 녹취·참석·녹화 조회 | 회의 유형·주최자·자료 생성 상태별 권한 확인. 저장 완료된 분할 녹화를 조회하고 채널 수업 참석 CSV는 Teams 웹 일정에서 다운로드 |
| SharePoint 파일 읽기·결과 저장 | `Sites.Selected`와 실제 사이트 허용 범위 확인 후 Drive API로 저장된 파일 다운로드·파싱. 별도 결과 파일만 지정 폴더에 저장하며 Excel 셀·Word 원문 수정은 사람이 수행 |
| Azure 비용 | 대상 구독의 Cost Management 조회 역할. 리소스 변경 권한은 분리 |

정확한 요청 권한은 실제 API 선택 후 권한 목록으로 고정하고 허용·거부를 배포 전 확인으로 함께 점검합니다.

## 6. 엑셀 일정표 기반 1개월 단위 수업 이벤트 생성 및 수업방 강사 구성원 연결

1. 사람이 편집·저장한 수업 일정표를 읽고, 대상 연월(`YYYY-MM`) 1개월의 기수별·수업일별 강의 1개와 시작/종료 시각·날짜별 담당 강사를 검증합니다. 같은 날짜에 여러 기수가 운영되어도 각 기수의 일정·채널·수신자를 구분합니다.
2. 실제 팀·채널 유형과 기존 강사 접근을 조회합니다. 구조·권한 영향이 미확정이면 매니저 확인 대기로 두고, 사전 승인된 범위의 구성원 추가만 자동 수행합니다.
3. 현재 매니저가 일일이 만드는 채널 수업 이벤트를 **`@dataschool` Teams 웹 일정에서 컴퓨터 사용으로 생성·수정**합니다. 대상 팀·채널·주최자·날짜와 생성된 회의 링크를 확인합니다.
4. 생성 결과 확인 후 Graph로 `@elixirr` 운영 일정에 같은 수업의 시간·참가 링크를 기록합니다. 별개의 일반 온라인 회의를 중복 생성하지 않습니다.
5. 실제 회의 유형·회의 링크·Teams 일정 참조·조회 가능한 외부 ID·직원 Outlook 이벤트 ID·생성 월·강사·원본 버전을 DB에 연결합니다. 확인하지 못한 ID는 임의 생성하지 않습니다.
6. 수업 편성 변경은 원본 일정표 확인 후 해당 회차에 반영합니다. Teams 또는 Outlook 반영 실패는 부분 동기화로 표시하고 잘못된 안내를 보류합니다.
7. 같은 수업 참조로 분할 녹화([F10](04_수업_자료와_학습_지원.md#f10))와 참석 CSV([F16](06_출결과_증빙_처리.md#f16))를 수집합니다. 녹취가 없는 채널 수업을 일반 회의 API로 조회할 수 있다고 가정하지 않습니다.

**회의 유형 구분:** Graph의 `isOnlineMeeting=true` 이벤트나 독립 `onlineMeeting` 생성은 채널 회의 생성과 같지 않습니다. 수업은 실제 Teams 채널 일정 생성에 맞추고, 일반 온라인 회의를 쓰는 별도 행사는 유형을 명시해 지원 API를 선택합니다. 라이선스·정책·주최자 권한·로그인 세션·채널 선택 동작은 배포 전에 확인합니다.

**파일 구조와 연결 확인:** 제공받은 경로 예시는 KDT 폴더 구조를 기준으로 하되, 기수별 운영 채널의 소속 팀·채널 유형 및 테넌트·사이트·드라이브·폴더 ID·권한은 실제 대상에서 확인해 등록합니다. 강사팀 `출석부` 읽기와 운영 채널 `출석부` 결과 저장을 별도 범위로 지정합니다. 예시 이름은 테스트 및 운영을 하면서 바꿀 수도 있으며, 이름만으로 다른 기수나 외부 공유 위치를 추정하지 않습니다.

## 7. 직원 로그인과 Teams 탭

직원 대시보드는 `@elixirr` 로그인을 기준으로 합니다. 회사 Teams 탭에서도 같은 화면을 엽니다. `@dataschool`에 탭을 설치하는 경우에는 해당 계정과 직원 역할을 확인한 계정만 허용합니다. 교육 계정으로 로그인했다는 이유로 직원 운영 화면을 열어주지 않습니다.

다른 테넌트 간 SSO가 자동 완성된다고 가정하지 않고, 지원되는 OAuth 로그인/팝업 또는 회사 웹 로그인 경로를 검증합니다.

## 8. 연결 마법사의 완료 조건

`테넌트 식별 → 앱/인증서 등록 → 관리자 동의 → 리소스 지정 → 배포 전 확인 → 바로 정식 운영 활성화`

- 토큰 발급 성공만으로 연결 완료라고 표시하지 않습니다.
- 읽기·쓰기·범위 밖 거부·만료 처리를 배포 전 확인 항목으로 구분하고, 운영 중에는 실패 시 경보합니다.
- 연결 변경은 이후 작업에 반영하되 이미 승인된 외부 전송의 내용·대상을 바꾸면 재승인합니다.
- 연결이 끊기면 학생 잘못으로 처리하지 않고 운영 연결 장애로 알립니다.

## 1. 확인 수준

이 문서의 리소스는 당시 공식 제품 문서를 조사한 **구현 후보·참고안**입니다. 지원 형식·API 버전·분석기·모델·SKU·리전은 실제 테스트·운영에서 바꿀 수 있으며 최종 제품 선택이나 지원 보증이 아닙니다. 계정·구독·권한·쿼터·정책 조회의 상세 확인값은 중복 관리하지 않고 실환경 확인 기록을 기준으로 합니다.

- **공식 기능 확인:** 해당 제품 문서가 설명하는 기능.
- **실환경 조회 기록:** 구독·관리자 역할·모델별 쿼터·정책 할당 목록은 실환경 확인 절의 확인 범위를 따릅니다. 조회 성공과 실제 배포·서비스 동작 성공은 다릅니다.
- **테스트·운영 확인:** 실제 연결·권한·대상·완료 조건을 확인해 운영에 적용하고, 모델 품질·속도·가성비·파싱 결과를 운영하면서 측정·개선합니다. 가격 후보의 품질을 사전에 확정했다고 주장하지 않습니다.

세 항목은 서로 대체하지 않습니다. 최신 제품이어도 구독에서 제공되지 않을 수 있고, 제공되어도 우리 사이트 자동화를 보장하지 않습니다.

## 2. 기준 리소스

### 2.1 리소스는 어디에 만들어지는가

- **새로 만드는 Azure 리소스는 모두 `@msacademy` 계정으로 접근하는 회사 엘릭서 구독**(`7ad28d1d-…`, 소속 디렉터리 `msaischool.onmicrosoft.com`)에 생성합니다. (R17 AI Search는 R07 벡터 검색으로 부족할 때만 도입합니다.)
- **리전은 고정하지 않습니다.** 아래 표의 `Korea Central`·`East US 2`는 조사·비교 당시의 배치 예시입니다. 상황에 따라 다른 리전에 생성하거나 다른 지역에서 처리하며 실제 테스트·운영에서 선택·변경합니다. 생성 위치·저장 위치·AI 처리 위치는 서로 다를 수 있고 Global 배포가 국내 처리만을 보장하지도 않습니다. 변경 시 정책·권한·데이터 이동·지연·비용을 확인합니다.
- **`@elixirr`·`@dataschool`에는 Azure 리소스를 만들지 않습니다.** 두 조직은 Azure 구독 없이 Entra **연결 앱 등록·관리자 동의**와 Teams 앱 설치만 합니다. 앱의 인증서는 엘릭서 구독의 R09 Key Vault에 보관합니다.
- **R18은 새로 만들지 않습니다.** `@elixirr`·`@dataschool`이 이미 쓰고 있는 M365(Exchange·Teams·SharePoint)를 연결해서 씁니다.
- **R18의 파일 위치는 KDT 폴더 구조를 참고합니다.** 수강생 팀 `일반`(배포 자료·녹화), 기수별 운영 채널(매뉴얼·상담·설문 결과·내부 출결), 강사팀(양식·보고서·평가문제·호명 출석부)을 구분합니다. 이 예시는 Azure 리소스나 신규 저장소를 만드는 지시가 아니며 실제 ID·권한·연동은 별도로 확인합니다.
- 아래 표의 **연결 계정** 열은 "그 리소스가 실제 업무 데이터를 주고받는 조직"입니다. 리소스 생성 위치와는 다른 개념입니다. 예를 들어 Container Apps는 엘릭서 구독에 생성되지만, 직원 대시보드는 `@elixirr` 로그인으로, 수업방 Teams 봇은 `@dataschool`로 연결됩니다.

### 2.3 선정 중심 조사 결과

**하루 일정과 여러 날의 강의 단위를 구분합니다.** 한 기수의 수업일당 일정은 1개이고, 만족도는 그 안의 각 `teaching_unit_id`가 끝날 때마다 객관식 2개·주관식 1개를 1회 받습니다. R11/F19 승인 템플릿 준비 → 강의별 R19 수집 연결 → 강의 종료 확인·안내 → DB 집계·결과 저장으로 처리합니다. UI·인증·양식별 연결은 실제 검증 대상이며, 공식 Forms 커넥터가 생성/복제를 제공한다고 가정하지 않습니다.

이 프로젝트의 업무는 대부분 **정해진 시각에 빠짐없이 실행되어야 하는 일**입니다. 1개월 단위 수업 이벤트 생성, 전날 강사 확인, 입퇴실·중간 출결, 퀴즈, 만족도 발송이 여기에 해당합니다. 1초 안에 응답해야 하는 일은 적습니다. 그래서 아래 순서로 판단했습니다.

1. **기능(신뢰성)을 먼저 봅니다.** 예약·재시도·복구·실패 대기함·보안처럼 없으면 업무가 깨지는 필수 기능은 생략하지 않습니다. 같은 기능을 충족하는 서비스·구현 방식은 비교해 바꿀 수 있습니다.
2. **기능이 충족되면 가격을 봅니다.** 사용량이 적고 들쭉날쭉하므로 고정 요금보다 사용량 과금·저가 등급부터 시작합니다.
3. **속도는 사람이 직접 기다리는 곳에만 따로 챙깁니다.** Teams 대화 응답과 대시보드가 여기에 해당합니다.

## 3. 최신 기준으로 반영한 중요한 선택

### Durable Task Scheduler

2026-10-15 갱신된 공식 문서는 Durable Task Scheduler를 Durable Functions의 권장 저장 공급자로 안내하고, Consumption·Dedicated 과금 SKU를 설명합니다. 따라서 본 설계는 이를 우선 검토합니다.

스케줄러 자체가 업무 코드를 모두 실행하는 것은 아닙니다. Functions의 실행 프로그램과 함께 사용합니다. 해당 구독·리전에서 적합하지 않으면 공식 지원 저장 공급자와 비교해 선택 사유를 기록합니다.

### Agent Service, Browser Automation, Computer use는 서로 다름

- Agent Service: 에이전트의 실행·도구 호출 관리.
- Browser Automation: Playwright 기반 브라우저 작업. 공식 문서상 GA.
- Computer use: 스크린샷을 보고 클릭·입력을 제안하는 모델 루프. 현재 가이드가 사용하는 모델은 `computer-use-preview`.
- Windows VM/PAD: 실제 Windows 앱 실행과 정형 PC 작업. computer use를 붙여도 세션·인증·화면 검증이 별도로 필요.

### 비정형 문서 파일(한글 `.hwp`/`.hwpx` · PDF · HTML · Word · PPT · 이미지)은 이렇게 저장·검색

**지원 정보의 해석:** 아래 형식 목록과 한도는 조사 당시 문서의 지원 정보를 정리한 후보이며 우리 환경의 검증 완료 목록이 아닙니다. 예를 들어 인용한 서비스 한도 문서에는 `2026-06-01-preview` 안내가 있으므로 선택 API·분석기에서 같은 기능을 쓸 수 있는지 확인합니다. 실제 테스트·운영에서는 `형식·API/분석기·리전·파서 버전·샘플·결과·확인일`을 기록하고 파서·변환기·서비스를 변경할 수 있습니다. 판독 불가 자료는 사람 확인으로 남깁니다.

수강생에게 받는 커리어 멘토링 사전 자료([F12](07_행사_멘토링_인재_관리.md#f12)), 지원서·포트폴리오([F02](03_모집과_OT_준비.md#f02)), 이력서([F13](07_행사_멘토링_인재_관리.md#f13)), 병가·출결 증빙([F14](06_출결과_증빙_처리.md#f14))과 강사 교안([F07](04_수업_자료와_학습_지원.md#f07))은 **워드(`.docx`)뿐 아니라 아래아한글(`.hwp`, `.hwpx`), `.pdf`, 웹/노션 내보내기 파일(`.html`, `.md`), `.pptx`, 스캔 이미지(`.jpg`, `.png`) 등 비정형 자료**를 입력 후보로 봅니다. 별도 DB 대신 아래 **3단계 파이프라인(원본 보관 → 형식별 추출·전처리 → PostgreSQL JSONB·벡터 통합 저장)**을 공통 처리 구조로 설계합니다. 모든 파일의 추출 성공을 보장하는 것은 아니며, 지원 여부·추출 실패·판독 불확실을 구분해 사람 확인으로 남깁니다.

| 단계 | 리소스 | 저장·처리 내용 |
|---|---|---|
| **1. 원본 파일 보관** | R18 SharePoint(우선) 또는 R08 Blob | 어떤 확장자(`.hwp`, `.hwpx`, `.pdf`, `.html`, `.docx`, `.pptx`, 이미지 등)든 원본 그대로 보관. 크기 제한·보관 기간·삭제 정책 적용 |
| **2. 형식별 내용·표 추출** | **① R16 Content Understanding (공식 기본 지원 형식)**<br>**② R02 서버 내 한글(`.hwp`/`.hwpx`) 전처리 파서·변환기** | · **R16 공식 기본 지원:** `.pdf`, `.html`, `.md`, `.txt`, `.rtf`, `.docx`/`.xlsx`/`.pptx`(매크로·구버전 `.doc`/`.xls`/`.ppt` 포함), `.odt`/`.ods`/`.odp`, `.csv`/`.json`/`.xml`, `.eml`/`.msg`, `.jpg`/`.png`/`.tiff` 등 (비동기 파일당 200MB 이하, PDF 300쪽 이하)<br>· **아래아한글(`.hwp`/`.hwpx`) 대응 (중요):** Microsoft R16은 한국 고유 포맷인 `.hwp`/`.hwpx`를 직접 지원하지 않으므로, **R02 컨테이너 서버에서 ① `.hwpx`(개방형 한글, ZIP+XML 구조)는 XML 본문·표 직접 파싱, ② `.hwp`(구형 바이너리)는 한글 파서(`pyhwp`/OLE 텍스트·표 추출) 또는 LibreOffice/전용 변환기로 `.pdf` 변환 후 R16에 전달**해 추출한 뒤 표·서식 누락을 검사하고, 변환 불가·판독 불확실 자료는 사람이 확인 |
| **3. 비정형 필드·검색·권한 저장** | **R07 PostgreSQL (`JSONB` + `pgvector`)** | · `documents` / `document_versions`: 원본 URI, 확장자·MIME(`file_ext`, `mime_type`), 파서 경로(`parser_type`: `content_understanding` / `hwpx_xml` / `hwp_to_pdf` / `html_dom`), 추출 상태(`parse_status`)<br>· **`extracted_fields (JSONB)`**: 문서마다 양식이 제각각인 비정형 항목(자소서 문항, 포트폴리오 링크, 경력·기술스택, 증빙 사유 등)을 고정 컬럼 없이 유연하게 구조화 저장<br>· `chunks` + `vector`: 추출된 본문·표 텍스트 조각과 임베딩 벡터 저장 → 퀴즈([F07](04_수업_자료와_학습_지원.md#f07))·멘토링 요약([F12](07_행사_멘토링_인재_관리.md#f12))·이력서 검색([F13](07_행사_멘토링_인재_관리.md#f13))에서 권한(`acl_bindings`)에 맞는 조각만 검색 |

파일 자체를 PostgreSQL에 넣지 않습니다. DB가 커지고 백업·복구가 느려지기 때문입니다. 검색 결과는 항상 원본 파일 위치로 되돌아갈 수 있게 연결합니다. 원본이 바뀌거나 삭제되면 추출 텍스트·JSONB·벡터도 함께 갱신·삭제합니다(데이터).


## 4. 공식 제공 상태와 본 설계의 사용 방법

**이 표는 무엇을 설명하나요?** Microsoft가 공식 문서에서 밝힌 **제품의 현재 상태**(정식 출시인지, 프리뷰(미리보기)인지, 어떤 조건·제약이 있는지)와, 그 상태 때문에 **본 설계가 그 리소스를 어떻게 제한해서 쓰는지**를 나란히 보여 줍니다. 즉 "리소스가 공식적으로 해 주는 것"과 "우리 설계가 실제로 기대하는 것" 사이의 차이(괴리)를 미리 드러내고 메우는 방법을 적은 표입니다.

읽는 법:

- **정식 출시(GA):** 운영에 써도 되는 단계. 그래도 하위 기능마다 상태가 다를 수 있습니다.
- **프리뷰(미리보기):** 서비스 수준 보장(SLA)이 없고 바뀔 수 있습니다. 본 설계는 프리뷰 기능을 **꺼도 핵심 운영이 멈추지 않게** 둡니다.
- **조건·제약:** 라이선스, 리전, 요금 등급처럼 써도 되지만 지켜야 하는 조건입니다.

| 리소스 | Microsoft 공식 상태 (쉬운 말) | 차이 때문에 본 설계가 정한 사용 방법 |
|---|---|---|
| Foundry Agent Service | 정식 출시. 단, 일부 하위 기능은 프리뷰 | 핵심 업무는 정식 기능만 사용. 하위 기능은 하나씩 상태 확인 후 추가 |
| Browser Automation | 정식 출시. 단, 사설(비공개) 사이트 접속은 공개 프리뷰 | 공개 접근 LMS 화면은 정식 기능으로 운영. 사설 사이트 접속은 프리뷰이므로 배포 전 확인 후 운영에 포함하고, 실패 시 PAD 정형 실행으로 대체 |

## 5. SKU·리전·모델을 선택·갱신하는 순서

리소스 이름을 정했다고 배치·비용·품질이 확정되는 것은 아닙니다. 아래는 테스트·운영에서 갱신하는 선택 절차이며 특정 리전·모델·일정의 승인 절차가 아닙니다.

1. API·DB·스토리지·모델별 제공 여부·쿼터·정책·지연·비용에 맞게 생성 리전을 선택합니다. 모든 서비스가 같은 리전이어야 한다고 가정하지 않습니다.
2. 생성 위치·저장 위치와 실제 AI 처리 위치를 구분하고 허용 조건 안에서 다른 리전·배포 유형을 사용하거나 이전합니다. Global 방식은 생성 리전 안에서만 처리된다는 뜻이 아닙니다.
3. Foundry의 모델별 쿼터는 실환경 확인 기록의 CLI 조회값을 기준으로 하고, 배포 SKU 및 단가 비교는 모델 가격 비교를 따릅니다.
4. 서비스·모델·API/분석기 조합의 제공 상태와 실제 동작을 테스트·운영에서 확인하고 변경 사유·적용 버전을 기록합니다.
5. 필요한 처리량과 보안 요구를 넣어 SKU를 선택합니다. 모델은 운영 중 품질·속도·비용을 보며 더 좋은 모델 또는 더 가성비 있는 모델로 교체합니다.

# F19. 컴퓨터 사용·새 사이트 작업

[전체 목록](00_보고서_안내.md)

난이도: 5

실행기·모델·리전·사이트 절차는 조사 기준의 참고 후보입니다. 실제 테스트·운영에서 결과 정확성·사람 개입률·지연·비용을 보고 더 좋은 모델/실행 방식 또는 더 가성비 있는 구성으로 변경하며 현재 후보를 고정하지 않습니다. 권한·승인·비밀 분리·완료 검사는 유지합니다.

## 목적

웹 LMS·중간출결·출결 업데이트 사이트처럼 API가 없는 화면에서 허용된 업무를 정형 절차로 실행하고, 화면이 예상과 다른 예외 구간만 제한적으로 탐색합니다. 실행 결과(성공·실패·시간·비용·증거)는 기록하며, 절차 변경은 개발자·운영자가 검토해 새 버전으로 등록합니다.

## 입력·설정

업무 목표, 허용 사이트·동작, 연결 계정 참조, 대상 과정/기간, 완료 검사, 최대 단계·시간·비용, 승인 필요 동작, 사용자 개입 담당자.

비밀번호는 안전한 연결 입력으로 받으며, 일반 대화·설계 문서·운영 로그에 남기지 않습니다.

**파일 작업의 대상 확인:** KDT 폴더 구조의 수강생 `일반`·기수별 운영 채널·강사팀을 별도 허용 범위로 등록합니다. 화면의 폴더명뿐 아니라 연결 테넌트·site/drive/folder ID·과정·자료 역할·읽기/쓰기 목적을 확인한 뒤 작업하며, 비슷한 월·주차·일자 이름만으로 녹화와 출석부를 혼동하지 않습니다. 이름·날짜·화면·세부 구성은 테스트 및 운영을 하면서 바꿀 수도 있습니다. 예시 등록은 검증된 실행 절차 등록과 다르며 확인되지 않은 폴더를 임의 생성하거나 자료를 학생 영역으로 복사하지 않습니다.

## 처리 구조

```text
업무 요청 → 권한·행동 범위 확인
→ 사이트/역할/업무에 맞는 절차 검색
→ 검증된 절차 실행 또는 제한 탐색
→ 화면·요소 관찰 → 동작 후보 → 서버 정책 검사 → 실행
→ 단계별 결과 확인
→ 최종 완료 검사
→ 실행 기록 저장(성공·실패·시간·비용·증거)
→ 실패·화면 변경 시 담당자 알림 → 개발자·운영자가 절차 수정 후 새 버전 등록
```

| 방식 | 사용처 | 특징 |
|---|---|---|

F06의 3항목 승인 템플릿을 강의 단위별 1개로 준비하고 과정명·기수·강의명·강사·기간/종료일·응답 설정을 치환합니다. course_id·teaching_unit_id·form_id·question_map을 함께 저장합니다. 객관식 두 행·주관식 하나·선택지·필수 설정·실제 링크를 검사하며, 복제된 문항 ID는 시험 응답으로 확인합니다.

복제된 form_id의 Logic Apps 수집 연결은 승인된 Azure 배치 경로로 구성합니다. 연결 확인 전 발송을 차단하며 복제 결과 불명 시 기존 양식을 대조합니다. 응답은 공식 커넥터로 수집하고 Excel은 복구·대조에 사용합니다. UI·OAuth·교차 테넌트·강의별 연결·종료 1회·중복 방지 검증을 통과한 절차만 활성화합니다([F06](05_강의_단위별_만족도.md#f06)).

## 리소스·권한

Foundry, Playwright Workspaces, Windows 실행 환경/PAD(필요 시), Key Vault, PostgreSQL/벡터 검색, Blob, Service Bus, Durable Functions.

브라우저/PC 실행기는 사이트·계정별 격리합니다. 같은 계정의 동시 조작은 잠금으로 제한하고, 사용자 업무용 노트북을 운영 실행기로 사용하지 않습니다.

## 저장 구조

| 종류 | 내용 | 원본 |
|---|---|---|
| 업무 상태 | 학생·출결·규칙·승인 | PostgreSQL |
| 절차 | 화면 조건·단계·완료 검사·복구 | 버전 관리된 절차 DB |
| 실행 기록 | 성공/실패·단계·시간·비용·증거 | DB + 제한된 Blob |
| 선호·대화 | 보고 형식·사용자 선호 | DB |

절차 필드: 사이트, 계정 역할, 업무, 버전, 전제 조건, 허용 동작, 단계, 기대 화면, 완료 검사, 실패 복구, 검증일, 성공/실패 횟수, 적용 상태.

## 예외·승인

- CAPTCHA·정책 차단은 우회하지 않고 확인 대기.
- 삭제·결제·공식 기록 정정·외부 최종 제출은 승인.
- 사이트 화면에 있는 지시문은 운영자 명령이 아님.
- 비밀 입력은 도구 수준 주입/마스킹을 검증. 분리할 수 없는 단계는 사람이 처리.
- 실패 사례를 성공 절차로 등록하지 않음. 절차 새 버전은 사람 검토 후 등록.
- 결과 불명인 발송·제출을 무조건 재시도하지 않음.
- UI 업데이트 감지 시 기존 절차를 검증 대기로 돌리고 버전별로 되돌릴 수 있게 함.

## 운영 품질 기준

운영 중 같은 대표 업무의 반복 실행 기록으로 결과 정확성·사람 개입률·시간·비용을 측정합니다. UI 변경·세션 만료·잘못된 날짜·중복 작업에서도 비허용 행동이 없어야 합니다. “클릭을 끝냈다”가 아니라 실제 업무 완료 조건을 통과해야 합니다.
