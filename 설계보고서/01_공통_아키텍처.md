# 공통 아키텍처

[문서 목록](00_보고서_안내.md)

기준일: 2026-10-28

**참고 설계:** 자료의 해석 기준을 따릅니다. 모델은 실제 테스트·운영에서 품질과 비용을 보고 교체하며, 리소스 생성·데이터 저장·AI 처리 위치는 상황별로 선택·변경합니다. 예산·일정·리전·지원 형식을 확정 약속으로 해석하지 않습니다.

## 1. 한 문장 설명

**AI는 업무를 이해하는 담당자, 예약 시스템은 시계를 보는 담당자, 실행 도구는 손발, DB는 공동 업무 장부입니다.** 역할을 분리해 AI 대화가 끝나거나 특정 사이트가 고장 나도 다른 업무를 계속합니다.



**일정 운영 기준(사용자 설명·캘린더 기준): 한 기수는 수업일마다 하루 강의 일정 1개를 운영하고, 같은 날짜에 여러 기수가 각각의 강의를 동시에 운영합니다.** 기수별 달력에는 해당 기수의 일별 강의 하나가 보이며, 전체 달력의 같은 날짜에 보이는 여러 강의는 서로 다른 기수의 일정입니다. 강사·과목은 날짜에 따라 바뀔 수 있고, 공동 멘토링의 복수 담당자도 하루 일정 하나에 연결합니다. 오전·오후 출결이나 분할 녹화는 같은 하루 강의의 내부 구간입니다.

## 2. 고정할 구조와 늘릴 부분

| 구역 | 하는 일 | 과정 증가 시 대응 |
|---|---|---|
| 운영 화면 | 과정·학생·일정·승인·사람이 할 일·진척도 | 같은 화면에 과정 추가, 역할별 조회 |
| 업무 API | 화면·파일 변경·외부 요청 검증 | 요청 처리 인스턴스 증가 |
| AI PM | 일정 해석·검색·문항 초안·요약 | 모델 한도·동시 호출량 조절 |
| 규칙·예약 | 기수별 하루 강의 1개의 시작·종료와 날짜별 강사·과목 기준 업무 시각 계산 | 과정별 규칙·예약 데이터 증가 |
| 작업 대기열 | 몰린 업무 대기·실패 분리 | 작업 종류·계정별 대기열 분리 |
| 실행기 | Teams 발송·일정 화면 조작·파일 처리·LMS 조회 | 실행기 확장, 같은 계정 작업 직렬화 |
| 공동 DB | 학생·강사 배정·설정·승인·실행 이력 | 인덱스·용량·읽기 성능 조절 |
| 자료 저장소 | 원본·결과 파일·허용된 증거 | 보관·삭제 정책 적용 |

기능마다 AI·DB·예약기를 별도로 만들지 않습니다.

## 3. 실제 처리 예시

기본 규칙은 한 번 등록하고 반복 업무는 일정에 맞춰 실행합니다. **과정 종료 만족도는 과정 종료 시 1회 객관식 2개·주관식 1개를 받으며, 에이전트가 승인된 양식을 준비·안내하고 응답을 자동 수집·집계**합니다. 최초 규칙 승인·중요 결정·인증/예외는 사람이 맡습니다. 원본 문서 편집과 퀴즈 검수·정답/게시 등의 사람 작업은 별도 유지하며, 자동 실행과 사람 대기를 구분합니다.

1. **일정표 읽기:** 매니저·강사가 Teams/SharePoint 공유 엑셀을 직접 편집·저장합니다. 폴더 구조 예시의 운영 채널 루트 시간표와 수강생 `일반 / 02. 시간표` 중 기준 원본과 배포본 관계를 지정하고, 에이전트는 기준 파일의 버전을 확인해 다운로드·파싱합니다. 수업 편성은 일정표, 직원 근무 일정은 Outlook을 기준으로 하며 원본 셀을 직접 덮어쓰지 않습니다.
2. **회차·강사 검증:** 한 기수의 하루 강의를 하나의 회차 ID로 연결하고 기수·수업일·시작/종료·담당 강사를 검증합니다. 권진욱 → 강명호 → 인선미처럼 날짜별 강사 교체를 반영하며, 공동 멘토링 담당자는 같은 하루 일정에 복수 배정합니다. 같은 날짜의 다른 기수 강의는 별도 회차·대상으로 처리합니다. 시간 정보가 없으면 사람이 보완합니다.
3. **1개월 단위 Teams 수업 생성:** 현재 매니저가 일일이 만드는 채널 수업 일정을 **Teams 웹 일정의 컴퓨터 사용**으로 생성·수정합니다. 대상 팀·채널·주최자·수업일을 확인하고 해당 월만 발행합니다. 다음 달은 DB에서 대기합니다. 실제 생성된 회의 링크를 Graph로 직원 Outlook 일정에 반영하며 별도의 일반 온라인 회의를 중복 생성하지 않습니다.
4. **강사 접근 준비:** 기존 가입과 채널 유형을 조회합니다. 표준 채널은 팀 멤버십, 비공개·공유 채널은 별도 가입 조건을 따릅니다. 현재 공통 팀에서는 다른 기수 자료가 보일 수 있습니다. 실제 구조와 권한 영향을 확인한 뒤 사전 승인된 구성원 추가만 자동 수행하고, 미확정이면 매니저 확인 대기로 둡니다.
5. **반복 업무 예약:** 수업 전날 해당 강사에게 교안·출석부·중간평가 확인을 요청합니다. 휴강·방학에는 관련 예약을 생략하고, 실행 직전 일정·강사 교체·기제출 여부를 다시 확인합니다.
6. **오전 자료로 오후 퀴즈 준비:** 하루 3~4개로 나뉘어 저장되는 녹화 중 **처음 저장 완료된 오전 구간**과 당일 교안을 분석합니다. 오후 배포 전 강사 검수·사람의 Forms 게시·링크 등록을 기다립니다. 파일 저장·처리가 늦으면 확인된 교안·진도만으로 초안을 만들고 근거 범위를 표시하거나, 진도도 불명확하면 생성 대기로 둡니다.
7. **역할별 실행·보관:** 학생 안내·강사 소통·내부 보고는 05의 역할 매핑을 따릅니다. 수강생 파일 공유는 `일반` 안에서만 하며 `05. 강의자료`·`Recordings`를 참고합니다. 강사팀 `출석부`의 호명 원본을 읽고, 내부 3종 원본·종합본은 **운영 채널 `출석부 / 월 / 주차 / 일자`**에 별도 파일로 보관합니다. 과정 종료 Forms 응답은 Logic Apps → Service Bus → DB로 수집하고 집계 Excel·요약을 운영 채널 `중간평가 및 설문`에 별도 저장합니다. 참가 신청·동의서 등 다른 목적 양식의 다운로드 결과·과정 종료 설문 복구 사본은 원천과 시각을 구분합니다. 외부 출석 업무는 기관·자료 버전·대상을 지정한 요청과 매니저 승인이 있을 때만 **출석 관리 팀**으로 전달합니다.
8. **과정 종료 시 1회 만족도:** 과정별 승인 템플릿(5점 선택형 문항 2개·주관식 1개)을 F19 실행기로 복제·설정하고 양식 ID·응답 링크·문항 매핑을 DB에 등록합니다. 양식별 Logic Apps 수집 연결 확인 후 각 기수의 과정 종료 시 1회 Teams로 안내합니다. 수집·검증·두 항목 점수 집계·주관식 요약·결과 저장을 자동 실행하며, UI·인증·수집 장애만 확인 대기로 둡니다([F06](기능/F06_만족도조사.md)).
9. **사전 출결 일정 대조:** 기수별 `01. 출결 게시판`의 지각·조퇴·외출 예정과 변경/취소를 LMS 입퇴실 확인 전에 수집합니다. 신고한 입실·퇴실·복귀 시각과 실제 기록·호명 출석부를 대조해 학생별 확인 예약과 안내를 갱신합니다. 접수된 신고는 일반 미클릭 독촉 방지에 반영하고 공식 인정·정정은 별도 상태로 둡니다. 게시판 수집 실패를 신고 없음으로 보지 않습니다([F15](기능/F15_LMS_입퇴실.md)).
10. **진척도 집계:** 파일 수집·일정 발행·사람의 작업·승인·외부 전달을 구분해 직원 대시보드에 표시합니다. 알림 발송을 실제 업무 완료로 간주하지 않습니다.

**구조 예시와 실제 연결의 구분:** 사용자 제공 구조를 자료 역할·경로의 참고 기준으로 반영했습니다. 날짜·강사명·파일명·세부 구성은 테스트 및 운영을 하면서 바꿀 수도 있습니다. 기수별 운영 채널의 소속 팀, 실제 채널 유형·사이트·드라이브·폴더 ID·권한은 별도 확인하며 미확인 연결은 보관 대기로 표시합니다. 폴더명만으로 임의 저장·외부 전달하지 않습니다.

## 4. Azure 배치 기준안

운영 인프라는 `@msacademy` 계정으로 접근하는 회사 **엘릭서 구독**(`msaischool.onmicrosoft.com`)에 둡니다. `@elixirr`·`@dataschool`에는 연결 앱·동의·Teams 앱을 구성합니다. 기존 리소스는 임의 변경하지 않으며 개발/운영의 권한·키·데이터·수신자를 분리합니다.

- **웹/API:** Container Apps. 직원 로그인은 `@elixirr`, 교육 Teams 연결은 `@dataschool`.
- **Forms 수집:** Logic Apps Consumption + Forms API 연결. 교육 조직 계정의 최초 OAuth 인증과 양식별 트리거 연결이 필요합니다. 설문 생성은 F19 브라우저 절차, 응답 수집은 공식 커넥터로 구분합니다.
- **AI:** Foundry Agent Service와 작업별 배포 모델. 권한·규칙의 최종 검사는 서버 코드.
- **예약:** Functions(Flex Consumption)의 Durable Functions + Durable Task Scheduler.
- **작업 전달:** Service Bus. 발송·문서·웹/PC 작업 분리.
- **운영 DB·검색:** PostgreSQL Flexible Server + `vector`, 운영용 General Purpose 2 vCore부터.
- **파일:** 기존 SharePoint/Teams 원본을 우선 사용하고, 필요한 처리 사본·증거는 Blob. Drive API로 저장된 파일을 읽고 별도 결과 파일을 쓰며 Excel 셀·Word 원문은 사람이 편집.
- **웹 자동화:** 검증된 Playwright 절차 또는 Foundry Browser Automation. Teams 채널 수업 생성·참석 CSV 다운로드·LMS 조회에 사용.
- **문서·영상 추출:** Content Understanding 및 한글 `.hwp`/`.hwpx` 전처리. 형식·분량·화질에 따라 실패·누락을 표시하고 사람 확인.
- **비밀·감시:** Key Vault, Managed Identity, Monitor/Application Insights.
- **화면 예외:** computer use는 선택 경로. 리전은 서비스·모델 제공 여부·쿼터·정책·지연·비용에 따라 실제 테스트·운영에서 선택·변경합니다. 조사 당시 지역별 제공 이력은 06을 참고하며 특정 지역에 영구 고정하지 않습니다.

리소스별 생성 위치·계정·SKU·상태·선정 이유는 [03 리소스](03_Azure_리소스_근거.md) 명세를 따릅니다. 리소스 그룹 분리는 구독 전체 장애·청구·상위 정책까지 분리하지는 않습니다.

## 5. 대기열과 예약기가 둘 다 필요한 이유

- **Durable Functions:** 시각 대기·사람 승인·재안내·복구 순서를 기억합니다.
- **Service Bus:** 지금 몰린 작업을 실행기 처리량에 맞게 전달합니다.
- **PostgreSQL:** 실제 업무·승인·결과의 원본입니다. 예약기 이력으로 업무 장부를 대체하지 않습니다.

업무 변경과 발행 예정 항목은 같은 DB 트랜잭션에 저장합니다. 별도 전달기가 대기열에 보내고 실행 키로 중복을 막는 outbox 방식을 사용합니다.

## 6. 업무가 몰려도 섞이지 않게 하기

1. 작업마다 `organization_id`, `course_id`, `connection_id`, `rule_version`, `run_id`를 기록합니다.
2. 과정별 우선순위와 동시 실행 한도를 둡니다.
3. 같은 사이트·계정의 로그인 세션은 잠금으로 직렬화합니다.
4. Graph·Teams 과다 요청은 지정된 대기시간을 지킵니다.
5. 반복 실패는 해당 연결만 중단하고 담당자에게 알립니다.
6. 모델에는 해당 업무의 허용된 자료만 전달합니다. 앱에 넓은 사이트 권한이 있어도 업무별 파일 범위를 서버에서 제한합니다.

처리량은 같은 시각의 작업 수와 작업당 시간·계정별 동시성으로 산정합니다. 측정 없이 무제한 확장이나 확정 성능을 주장하지 않습니다.

## 7. 설정 변경과 새 개발의 구분

| 변경 | 처리 |
|---|---|
| 기존 기능의 시각·대상·재안내·기간 변경 | 설정 버전 변경과 예약 재계산 |
| 체크리스트 항목·엑셀 컬럼 변경 | 양식 버전·컬럼 매핑 검사, 모호한 항목은 사람 확인 |
| 등록된 도구로 새 업무 조합 | 허용 동작·의존성 검증 |
| 새 사이트·미지원 파일 형식·새 권한 | 연결·파서·절차 개발 또는 관리자 설정 후 배포 전 확인 |
| 운영 코드 교체 | 개발 환경 작업·사람 검토·승인 후 배포 |
