## 1. 현재 범위

**새 시스템을 구축합니다. 지금은 세 계정을 연결하는 방법과 필요한 권한만 확인합니다.** 아직 기존 리소스 변경·신규 앱 등록·관리자 동의 실행은 하지 않은 상태입니다.

## 2. 쉬운 연결 구조

```text
@elixirr 직원이 회사 계정으로 로그인
                  │
                  ▼
@msacademy 계정으로 관리하는 ‘엘릭서’ Azure 구독
       새 AI PM 서버 / DB / 예약 실행기
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
@elixirr용 연결 앱      @dataschool용 연결 앱
회사 관리자가 허용      교육 관리자가 허용
        │                   │
```

계정·비밀번호를 합치는 것이 아닙니다. 각 조직에서 **“이 프로그램은 이 일정과 이 팀에 접근해도 된다”**고 허가하고, 중앙 서버가 해당 허가로 작업합니다.

회사/교육 조직에 Azure 구독이 없어도 Entra 앱 등록과 M365 데이터 연결은 가능합니다. 실제 서비스 라이선스·정책은 별도로 충족해야 합니다.

## 3. 실환경 기준 문서

**계정·구독 ID·테넌트 ID·역할·라이선스·쿼터·정책 조회값과 확인일은 06 실환경 확인 기록을 기준으로 합니다.** 이 문서에서는 상세 스펙을 중복 관리하지 않습니다. 세 계정 관리자 역할과 정책 할당 목록 조회는 확인되었으나 신규 앱 동의·실제 배포·업무 연결 성공은 별도 확인 대상입니다.

모델·리전·지원 형식·예산·일정은 공통 참고 기준에 따라 테스트·운영에서 변경 가능합니다. 미확정 참고값 자체를 워크샵 자료의 승인 차단 사유로 해석하지 않습니다.

## 6. 연결 작업별 권한

| 업무 | 확인할 권한·설정 | 주의점 |
|---|---|---|
| 직원 로그인 | 회사 테넌트 앱, 리디렉션 URI, 허용 사용자·운영 역할 | 로그인 성공만으로 모든 과정 권한을 주지 않음 |
| Outlook 일정 조회/변경 | 지정 메일함의 일정 앱 권한/Exchange Application RBAC | 조직 전체 메일함으로 범위를 넓히지 않음 |
| 업무 메일 발송 | 지정 발신자 범위 | 메일 읽기와 발송 권한을 구분 |
| Teams 알림 | Teams 앱/봇 등록·설치·대화 컨텍스트 | Graph 관리자 동의만으로 설치가 완료되는 것은 아님 |
| Teams 채널·채팅 읽기 | 지원되는 RSC 또는 필요한 Graph 권한 | 팀·채팅·회의의 범위를 구분 |
| 채널 수업 일정 생성 | `@dataschool` Teams 웹 일정의 컴퓨터 사용, 실제 주최자·팀·채널 선택 | 일반 Graph 온라인 회의 생성과 다름. Teams 로그인·MFA·조건부 접근·화면 절차를 별도 확인 |
| 녹취·녹화·참석 조회 | 회의 유형별 권한·파일 접근·자료 생성 상태 | 오전 분할 녹화의 저장 완료 확인. 참석 CSV는 같은 채널 수업 일정에서 UI 다운로드 |
| SharePoint 자료 | 지정 사이트 접근 권한 | `Sites.Selected` 동의와 실제 사이트 허용은 둘 다 필요 |

정확한 Graph 권한 이름과 승인 경로는 사용할 API가 정해진 뒤 목록으로 고정합니다. “Global Administrator를 에이전트에 주면 해결”하는 방식은 사용하지 않습니다.

### 공식 권한 이름으로 표현한 요청 후보

다음은 실제 제품 문서에 있는 후보입니다. **전부 일괄 부여하는 목록이 아닙니다.** 선택한 작업·대상 범위에 필요한 항목만 요청합니다.

| 용도 | 권한/역할 후보 | 적용 조건 |
|---|---|---|
| 지정 일정 읽기 | Exchange `Application Calendars.Read` | 대상 메일함 범위와 함께 부여 |
| 지정 일정 생성·변경 | Exchange `Application Calendars.ReadWrite` | 일정 읽기만 필요하면 사용하지 않음 |
| 지정 발신자 메일 전송 | Exchange `Application Mail.Send` | 필요한 발신 메일함으로 제한 |
| 팀 강사 구성원 추가 | Graph `TeamMember.ReadWrite.All` 또는 작업에 지원되는 최소 범위 | 표준 채널은 팀 가입을 따름. 공통 팀 가입으로 다른 기수 자료가 보일 수 있으므로 실제 구조와 사전 승인 범위 확인 |
| 비공개·공유 채널 강사 추가 | Graph `ChannelMember.ReadWrite.All` 등 해당 API 지원 권한 | 표준 채널 가입의 대체 권한이 아님. 채널 유형·참여 조건·기존 팀 관계 확인 후 사용 |
| 특정 팀의 채널 읽기 | Teams RSC `ChannelMessage.Read.Group` | 해당 팀에 앱 설치·리소스 동의 |
| 특정 채팅 읽기 | Teams RSC `ChatMessage.Read.Chat` | 해당 채팅 범위 동의 |
| 특정 팀 채널 발송 | Teams RSC `ChannelMessage.Send.Group` 또는 지원되는 봇 발송 경로 | 실제 API/SDK·가용 상태·설치 조건 확인 |
| 특정 회의 녹취 | Teams RSC `OnlineMeetingTranscript.Read.Chat` | 회의/채팅 범위·자료 생성 조건 |
| 특정 회의 녹화 | Teams RSC `OnlineMeetingRecording.Read.Chat` | 회의/채팅 범위·자료 생성 조건 |
| 지정 SharePoint 파일 읽기·별도 결과 파일 저장 | Graph `Sites.Selected` + 대상 사이트의 작업별 허용 범위 | Drive API 다운로드·파싱 및 지정 결과 폴더 쓰기. Excel 셀 API의 애플리케이션 권한은 미지원이며 Word 원문 편집도 별개. 원본 수정은 사람이 수행 |

RSC 문서는 일부 권한에 연결된 기능이 GA가 아닐 수 있다고 안내합니다. 권한 이름이 목록에 있다는 것과 선택한 API 조합이 운영 가능하다는 것을 구분해 배포 전 확인합니다.

Exchange Application RBAC와 Entra에 직접 부여한 전역 권한은 독립 경로입니다. 범위 제한을 해 놓고 전역 권한을 함께 부여해 제한을 무력화하지 않도록 합니다. `Test-ServicePrincipalAuthorization` 검사만으로 Entra의 별도 권한까지 검사되는 것은 아니므로 실제 API의 범위 밖 거부도 확인합니다.

## 7. 관리자 역할 해석

- Azure Owner: 해당 구독의 리소스·Azure RBAC 관리.
- Entra Global Administrator/적절한 동의 관리자: 해당 조직의 앱·권한 승인.
- Teams Administrator: Teams 정책·앱 관리.
- Exchange Administrator: 메일·일정 관련 설정.
- Power Platform 환경 역할/Dataverse 역할: Copilot Studio를 사용할 때의 별도 조건.

세 계정(`@msacademy`, `@elixirr`, `@dataschool`) 모두 현재 사용자 계정에 **Global Administrator** 역할이 있음을 확인했습니다. 다만 관리자 계정의 전체 권한을 에이전트에 그대로 부여하지 않고, 각 조직에 신규 연결 앱을 등록해 아래 최소 권한만 부여합니다.

### 회사(`@elixirr`) 및 교육(`@dataschool`) 테넌트에 직접 설정할 최소 범위

1. 신규 연결 앱 등록 및 소유자 지정.
2. 합의된 Graph 애플리케이션 권한 및 RSC 권한에 대한 관리자 동의.
3. Exchange Application RBAC로 지정 캘린더·발신 메일함 범위 제한 설정.
4. Teams 앱 설치·사용 정책 및 보고/안내 대상 채널 설정.
5. 회사 직원 로그인 앱의 허용 사용자/그룹과 운영 역할 설정.

## 8. 연결 방식의 선택

현재 기준안은 **테넌트별 앱을 중앙 서버에 연결**하는 방식입니다. 세 조직의 승인을 각각 명확하게 검증하기 쉽습니다.

향후 연결 기관이 많이 늘면 멀티테넌트 앱과 조직별 서비스 주체·관리자 동의로 설치를 표준화할 수 있습니다. 멀티테넌트 앱도 상대 조직의 동의는 필요합니다.

단순 API 연결을 위해 직원·학생 전체를 B2B 게스트로 복제하거나 테넌트를 합병할 필요는 없습니다. 특정 UI·협업 기능에 필요한 교차 테넌트 설정은 해당 기능에 한정해 판단합니다.

   - `③ 강사팀`: `{기수} 강사팀`의 양식·결과보고서·멘토링 일지·산출물·중간평가문제·출석부. `출석부`의 호명 원본 읽기와 학생 배포 자료를 구분.
   - `④ 기수별 운영 채널`: `{기수} 채널 / 공유 탭`의 매뉴얼·상담·설문 결과·행사 자료와 **`출석부 / 월 / 주차 / 일자`** 내부 원본·종합본 보관. 소속 팀·실제 권한은 미확정이며 수강생 팀으로 간주하지 않음.
5. 필요한 파일의 허용 범위 읽기·버전 대조와 지정 폴더 결과 저장 확인. 현재 M365에서 다른 기수 자료가 보이는 것과 에이전트의 업무별 접근 제한을 구분. 원본 셀을 무인 수정하지 않는지 확인.

7. 권한 회수·앱 제거·인증서 만료 시 중단과 담당자 알림.

### H. 규모·비용·장애 운영 — 용량 설계 전

- [ ] 한 기수 수업일당 강의 일정 1개, 같은 날 여러 기수 동시 운영을 기준으로 과정·학생·강사 수와 기수별 하루 메시지·파일·영상량 산정. 같은 기수의 중복 일별 일정 감지와 기수 간 수신자/응답 분리 확인.
- [ ] 집중 실행 시간·작업당 시간·동시 PC 계정/작업 수.
- [ ] 예약·데이터 수집의 허용 지연과 월/작업별 비용 상한.
- [ ] Azure 조회 비용(청구 전 추정)·사용 로그 추정·배분의 원천/기간/통화/수집 시각, 중복 제외·대조 불가 별도 표시, 비용 경보 기준.
- [ ] 장애 수신자·대응 시간·복구 목표시간(RTO)·허용 손실(RPO).
- [ ] 승인·콘텐츠 검수·비용·배포·백업 담당자.

### I. 배포 전 확인·운영 품질 기준 — 정식 운영 배포 시

- [ ] 바로 연결할 실제 운영 대상(직원·강사·학생 계정, 수업방·채팅·일정·메일함·사이트) 지정.
- [ ] 운영 중 오류/중복/누락/예외 사례를 자동 기록·분류하는 기준.
- [ ] 실제 운영 LMS·외부 사이트의 연결 대상과 허용 범위.
- [ ] 오발송·중복·권한 밖 접근·일정 취소 반영의 운영 품질 기준(05 3절)과 기준 이탈 시 자동 중단 조건.
- [ ] AI 요약·문항·경보의 운영 중 정확도 측정(담당자 수정률·오탐 기록) 방법.
- [ ] 화면 변경·인증 만료·권한 회수·장애의 자동 감지와 백업 복구 절차.
- [ ] 노트북/사용자 로그아웃 이후 서버 자동 실행 여부를 운영 감시로 상시 확인.

각 항목은 배포 전 화면/API 확인·관리자 회신·운영국 확정 규칙 등으로 근거를 확보한 뒤 06에 기록하고 여기서 삭제합니다. “관리자 요청 발송”, “관리자 역할 보유”, “앱 설정 저장”만으로 실제 연결 확인까지 완료 처리하지 않습니다.
